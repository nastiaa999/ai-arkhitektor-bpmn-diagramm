# BPMN-архитектор

ИИ-помощник для бизнес-аналитиков: превращает текстовое описание бизнес-процесса в готовую диаграмму **BPMN 2.0**.

```
Текст процесса → LLM → ProcessIR (JSON) → линтер логики с автоисправлением
                                              → раскладка + BPMN 2.0 XML → XSD-валидация → UI / bpmn.io
```

Результат — обычный файл BPMN 2.0 XML: он проходит валидацию по официальной XSD-схеме и открывается
без доработок и конвертаций в **bpmn.io** и любом другом редакторе, поддерживающем стандарт.

## Структура проекта

```
arkhitektor-bpmn-diagramm/
├── app/
│   ├── api/            # FastAPI-сервер: server.py — эндпоинты /api/generate, /api/validate
│   ├── pipeline/        # текст → IR: preprocess.py (нумерация предложений), extract.py (вызов LLM),
│   │                     # orchestrator.py (build_ir — связывает весь путь текст → IR)
│   ├── model/           # ir.py — Pydantic-схема ProcessIR (контракт между всеми модулями)
│   ├── lint/             # rules.py — правила L01–L12, clarify.py — замечания → вопросы пользователю
│   ├── llm/              # client.py — клиент GigaChat/OpenAI-compat, parse.py — разбор ответа модели
│   ├── export/           # pipeline.py — build_diagram(), bpmn_xml.py — сборка BPMN 2.0 XML
│   ├── layout/           # engine.py — автоматическое расположение элементов на холсте
│   ├── validate/         # xsd.py — проверка XML, xsd/ — официальные XSD-схемы стандарта BPMN 2.0
│   ├── prompts/           # flow.md — системный промпт, fewshot/ — примеры для few-shot
│   ├── config.py          # пути, настройки окружения
│   └── models.yaml        # профили LLM-провайдеров (gigachat, openai_compat и т.д.)
├── web/
│   └── index.html          # веб-интерфейс (дергает API, показывает диаграмму)
├── examples/inputs/         # примеры текстов процессов для демо и тестов
├── tests/                    # pytest: test_extract.py, test_lint.py, test_parse.py
├── cli.py                     # запуск без веб-интерфейса: generate, batch, ping
├── Dockerfile, docker-compose.yml, .dockerignore   # контейнеризация
├── requirements.txt
└── .env.example                # шаблон переменных окружения (ключи GigaChat и т.д.)
```

## Установка (с нуля)
Требуется Python 3.11+
1. Зайти на GitLab в репозиторий проекта.
2. Получить **Personal Access Token** (Profile → Access Tokens) и **сразу сохранить его себе в файл** —
   повторно посмотреть токен после создания будет нельзя, только пересоздать новый.
3. Клонировать репозиторий:
   ```bash
   git clone https://git.codenrock.com/codenrock/ii-assistenty/betmeny/arkhitektor-bpmn-diagramm
   ```
   Git попросит **логин** (смотрите в своём профиле на GitLab) и **пароль** —
   в поле пароля вставляется не пароль от аккаунта, а тот самый **Personal Access Token** из шага 2.
4. Открыть командную строку в папке проекта (дальше — см. «Запуск»).

## Запуск веб-сервиса

```bash
python -m venv venv && source venv/bin/activate      # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                                  # впишите GIGACHAT_CREDENTIALS
uvicorn app.api.server:app --reload
```
Открыть в браузере: **http://127.0.0.1:8000** — там же лежит веб-интерфейс (папка `web/`),
который дергает API и сразу показывает готовую диаграмму.

> Если вместо venv `venv` у вас уже используется `.venv` (как в CLI-сценарии ниже) — активируйте тот,
> который реально создали; команда одна и та же, просто с другим именем папки.

## Запуск в Docker (для демо и публичного доступа)

Публичная ссылка для жюри (ngrok, один раз настроить):

## API

| Метод | Путь | Вход | Выход |
|---|---|---|---|
| `POST` | `/api/generate` | `{ text, model? }` | `{ bpmn_xml, element_map, ir, issues, sentences, validation: { xsd }, metrics, clarifications }` |
| `POST` | `/api/validate` | `{ xml }` | `{ xsd }` |

`bpmn_xml` — готовый файл BPMN 2.0 (его можно сразу сохранить как `.bpmn` и открыть в bpmn.io).
`validation.xsd` — результат проверки этого же файла по официальной XSD-схеме стандарта.
`clarifications` — вопросы для диалога-уточнения, если описание процесса неполное.

## Примеры текста для построения диаграммы

**Отпуск сотрудника:**
```
Сотрудник подаёт заявление на отпуск своему руководителю. Руководитель проверяет, не пересекается ли
отпуск с графиком работы отдела. Если пересечения нет, руководитель подписывает заявление и передаёт
его в отдел кадров. Если пересечение есть, руководитель возвращает заявление сотруднику с просьбой
выбрать другие даты, и сотрудник подаёт новое заявление. Специалист отдела кадров оформляет приказ
об отпуске и уведомляет сотрудника.
```

**Закупка товаров и услуг:**
```
Инициатор составляет заявку на закупку и отправляет её в отдел закупок. Специалист отдела закупок
проверяет, что заявка заполнена корректно. Если в заявке есть ошибки, он возвращает её инициатору
на доработку, и инициатор исправляет заявку и отправляет повторно. Если заявка корректна, специалист
отдела закупок проверяет её стоимость. Если сумма превышает 100 тысяч рублей, заявку согласует
финансовый директор. Если сумма не превышает 100 тысяч рублей, заявку согласует руководитель закупок.
Если заявка согласована, информационная система 1С:УПП автоматически регистрирует её в реестре
закупок, и процесс завершается. Если заявка не согласована, специалист отдела закупок уведомляет
инициатора об отказе.
```

## Подключение GigaChat (бесплатный тариф)
1. Зайдите в https://developers.sber.ru/studio, создайте проект **GigaChat API**.
2. В проекте получите **«Ключ авторизации»** (строка в base64) → `GIGACHAT_CREDENTIALS` в `.env`.
   Scope по умолчанию `GIGACHAT_API_PERS` (физлица).
3. **TLS.** Сервер GigaChat использует сертификат НУЦ Минцифры, которого нет в `certifi`.
   Скачайте корневой сертификат (на странице Минцифры/Госуслуг «Установка сертификатов») и пропишите путь
   в `GIGACHAT_CA_BUNDLE=/path/to/russian_trusted_root_ca.pem`.
   Для быстрой локальной отладки можно `GIGACHAT_VERIFY_SSL=false` (для постоянной работы лучше подключить сертификат).
4. Модель задаётся `GIGACHAT_MODEL` (по умолчанию `GigaChat-2`). Если API вернёт 404/400 по модели —
   поставьте `GigaChat` или то, что доступно вашему тарифу.
5. Токен доступа живёт 30 минут, клиент обновляет его сам. Бесплатный тариф ограничивает параллельность,
   поэтому запросы идут по одному (в `batch` — последовательно).

## Смена модели
Одна строка в `.env`: `LLM_PROFILE=gigachat | openai_compat | gpt-oss-120b | yandexgpt` (или `--model` в CLI).
Профили — в `app/models.yaml`. Для любого OpenAI-совместимого API заполните `LLM_BASE_URL`, `LLM_MODEL`,
`LLM_API_KEY` и используйте `openai_compat`. Код при этом не меняется — провайдер подключается конфигурацией.

## Что сделано
| Модуль | Файл | Статус |
|---|---|---|
| IR-контракт | `app/model/ir.py` | Pydantic v2, «мягкие» валидаторы (алиасы типов, `next` строкой и т.д.) |
| LLM-адаптер | `app/llm/` | GigaChat (OAuth) + OpenAI-compat; снятие `<think>`/```json, `json_repair`, повтор при невалидном JSON, ретраи 429/5xx (2 и 6 с) |
| Предобработка | `app/pipeline/preprocess.py` | нумерация предложений, пункты списка = отдельные предложения (razdel) |
| Извлечение | `app/pipeline/extract.py`, `app/prompts/flow.md` | 1 вызов LLM, правила 1–10 + few-shot, повтор при ошибке схемы |
| Линтер | `app/lint/rules.py` | L01–L12: структурные проверки + автопереподключение изолированных (L09) и повисших параллельных (L12) веток; L08, L10 — лёгкие warning-правила |
| Диалог-уточнение | `app/lint/clarify.py` | неисправимые замечания линтера → вопросы пользователю (`clarifications`) |
| Оркестрация | `app/pipeline/orchestrator.py` | `build_ir()` — весь путь текст → IR, с дампом в `runs/<run_id>/` |
| Раскладка и экспорт | `app/export/pipeline.py` | `build_diagram()` — авторасположение элементов на холсте + сборка BPMN 2.0 XML |
| XSD-валидация | `app/validate/xsd.py` | проверка готового XML по официальной схеме стандарта |
| API-сервер | `app/api/server.py` | FastAPI: `/api/generate`, `/api/validate`, отдаёт веб-интерфейс (`web/`) |
| CLI | `cli.py` | `generate`, `batch`, `ping` |

## Контракт
```python
from app.pipeline.orchestrator import build_ir
from app.export.pipeline import build_diagram

res = build_ir(text, model=None)
res.ir             # ProcessIR после линтера: есть start, нет тупиков, разветвления/слияния только шлюзами
res.issues         # list[Issue]  {code, severity, message, step_ids, src, autofixed}
res.sentences      # для подсветки в UI
res.clarifications # list[dict] {question, step, code, step_ids, src} — вопросы для диалога-уточнения

diagram = build_diagram(res.ir.model_dump())
diagram["bpmn_xml"]      # готовый файл BPMN 2.0
diagram["element_map"]   # соответствие шагов IR элементам на диаграмме
diagram["metrics"]       # метрики раскладки/диаграммы
```
Автодобавленные шаги имеют `origin == "autofix"`.

## Что гарантирует линтер на выходе
Есть `start`; у каждого не-`end` шага ровно один выход (иначе — шлюз); `end` без выходов;
несколько входов в обычный шаг — только через шлюз-слияние (тип = ближайший доминирующий шлюз, по умолчанию `xor`);
шаги без входящих потоков (пропущенная ветка) по возможности подключаются как ветка «иначе» ближайшего
по тексту шлюза (L09); повисшие параллельные ветки переподключаются к ближайшему слиянию (L12);
все ссылки на шаги/участников существуют. Неисправимое (`error`, L01) остаётся в `issues` и уходит
в `clarifications` — пользователь может доуточнить процесс, вместо того чтобы получить на выходе
молчаливо додуманную диаграмму.

## Ограничения MVP
Один вызов LLM на текст (без цикла самоисправления через LLM); диаграмма строится для одного участника —
несколько пулов и обмен сообщениями между ними (message flows) не поддерживаются; тексты длиннее
150 предложений не делятся на части; качество зависит от модели — GigaChat-Lite может путать участников
в пассивном залоге.
